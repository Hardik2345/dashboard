01 Audit Validation Summary

The prior audit's live-measured findings hold up. Its recommendations don't all survive contact with the exact code. Two corrections stand out:

Finding 2 was wrong, not just unproven. The audit said Payment Split Trend's N+1 loop could be fixed by "using the ranged API that already works elsewhere." Reading the actual SQL in getOrderSplit/getPaymentSalesSplit shows every query branch collapses the requested range into a single row — there is no date/hour GROUP BY anywhere in this endpoint, and no granularity parameter exists at the controller layer. The "working precedent" cited never needed a bucketed response either. This is new backend work, not a call-site swap.

A previously unflagged infrastructure constraint changes Finding 3. Tenant MySQL connections are pooled by host:port:user, and the brands sampled all resolved to the same RDS host — meaning the connection pool (default cap of 5) may be shared across many brands, not per-brand. Blindly wrapping getDashboardSummary's 8 branches in Promise.all could exhaust that shared pool under real concurrent traffic. This needs a bounded-concurrency benchmark, not maximum parallelism.

Everything else in the original audit was confirmed, several findings were sharpened with exact query text, and one worse-than-reported issue surfaced: Product Conversion's inventory-sort and CSV export paths have zero row cap anywhere in the code — not just inefficient, genuinely unbounded.

06 Database Index Validation Plan

Current query (filtered daily branch)

SELECT created_date AS date, COUNT(DISTINCT order_name) AS orders,
       COALESCE(SUM(total_price), 0) AS sales
FROM shopify_orders
WHERE created_date >= ? AND created_date <= ?
  [+ equality/IN filters: utm_source, order_app_name, user_agent LIKE, product_id]
GROUP BY created_date ORDER BY created_date ASC

Hourly branch adds AND HOUR(created_time) <= ?; queryOrderSalesTotals's cutoff uses AND created_time < ? instead — two incompatible cutoff shapes, one index can't serve both without a generated column. When a product filter is active, the sales expression changes entirely (line-item based, not total_price).

07 API Optimization Plan

Payment Split Trend

Current: one HTTP call per hour/day × 2 endpoints × up to 2 ranges. Target: one call per series with a granularity=hourly|daily param, returning an array of per-bucket rows via GROUP BY DATE(created_date) (or + hour) instead of today's GROUP BY payment_type-only shape. This is a new response shape (array vs. object) — must be opt-in via the granularity param so useDashboardModeOfPaymentData's existing single-aggregate contract stays untouched. Ship behind a flag, verify in isolation, then migrate the frontend loop, keeping the old path available until verified.

Product Conversion

Current: sequential COUNT then SELECT, each re-deriving the same core CTEs; two paths with zero row cap. Target (pending MySQL-version confirmation): fold COUNT(*) OVER() into the SELECT to drop the separate round-trip for the common path; add a hard page cap to the inventory-sort/CSV paths regardless of the CTE decision. Validate identical output across all 8 benchmark brands before removing the old path.

08 Concurrency Strategy

The independent branches in getDashboardSummary are proven independent — no data flows between them. But connection pooling is keyed by host:port:user, and every brand sampled this session shares one RDS host, so the real pool may be shared across many brands at a default cap of 5. An unbounded 8-way Promise.all for one request could consume most of that shared pool and stall other brands' concurrent traffic.

Benchmark before choosing: serial (control), full parallel, and concurrency limits 2/3/4 — measured both in isolation and under 5 simultaneous requests (same and different brands). Starting point for the first controlled experiment: limit 3 — adjust based on measured queue depth, not assumed.

Success: latency drops materially at the chosen limit with no measurable queue-depth/tail-latency regression for concurrent traffic. Failure: any level that increases p95/p99 for other requests or produces connection-acquisition timeouts. Rollback: concurrency limit is a config value, defaulting back to serial (limit 1) with no deploy required.
