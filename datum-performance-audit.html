01 Executive Summary

The primary bottleneck is the database layer — specifically query shape, not raw data volume or the database engine itself. The same 30-day daily-funnel query ran in 654ms on a small brand and 109.6 seconds on a large brand against the same MySQL cluster, same schema, same code. The live EXPLAIN plan proves why: the query does COUNT(DISTINCT order_name), but every date-prefixed index on shopify_orders was built around order_id, total_price, or UTM columns — none index order_name — so MySQL falls back to scanning the table's entire index (1.88M rows) in date order instead of seeking to a 30-day range.

This is compounded by an application-layer pattern found across nearly every KPI/trend/funnel endpoint in analytics: independent sub-queries (returns, checkout-initiated, intent, row-two comparisons, current vs. previous period) are awaited one after another instead of run concurrently, and several endpoints re-run the same expensive scan twice per request (once for a `COUNT`, once for the `SELECT`, or once per comparison period) instead of once. Neither of these is data-volume-proportional in a way indexing alone fixes — they multiply whatever the single-query cost already is.

The frontend is a secondary but real contributor: one chart view (hourly/daily Payment Split Trend, in both widgetDataHooks.js and HourlySalesCompare.jsx) generates up to ~97 backend requests for a single hourly render and ~360 for a 90-day daily range, by looping one HTTP call per hour/day client-side instead of requesting a range the backend already knows how to aggregate. The gateway itself is not a factor — JWT verification is O(1) and cached, with no per-request database or tenant-router round trip in the common case.

Bottlenecks that specifically worsen with brand size: the COUNT(DISTINCT order_name) query shape (scales with total shopify_orders row count — line-item grain, so multiplies with average items-per-order too); the Product Conversion Table's unbounded, unpaginated CTEs (scale with total product/date-range row count, and run twice per page load); the serial sub-query fan-out in getDashboardSummary (scales with the number of independent branches taken, each against a large table). Bottlenecks that do not depend on brand size: the frontend N+1 chart loops (fixed at ~24 or ~90 iterations regardless of brand), and alerts-service's full-fcm_tokens-scan-per-notification (scales with total registered devices across the whole org, not per-brand).

Root cause: the query selects COUNT(DISTINCT order_name), but neither candidate index ((created_date, total_price) or (created_date, order_id)) contains order_name. MySQL can use created_date to satisfy the GROUP BY ordering by walking the whole index, but can't use it to seek a 30-day range while also resolving order_name without a full scan — so it reads all 1.88M index entries and does a lookup per row.

shopify_orders is line-item grain (unique key order_id + line_item_id), confirmed via SHOW INDEX — every order with N line items contributes N rows, which is exactly why the query needs DISTINCT in the first place, and why row count (and therefore scan cost) grows faster than order count as a brand's catalog/basket size grows.

03 Top Bottlenecks

P0

Daily-funnel / trend queries do COUNT(DISTINCT) with no covering index

Endpoints
Conversion Funnel panel, hourly/daily trend chart — any view with a product/device/UTM/discount/sales-channel filter active (fetchDailyRows/fetchHourlyRows, metricsSnapshotService.js:1715-1897)
Evidence
Live-measured 654ms → 109,643ms across 8 brands; EXPLAIN shows type: index over all 1.88M rows instead of a range seek (Section 2)
Root cause
No index on shopify_orders covers (created_date, order_name); the query needs order_name for DISTINCT but every date-prefixed index was built around a different column
Worse for large brands
Scales with total line-item row count (orders × avg. items/order) in the queried date range — a full-index scan, so cost is roughly linear in table size for any brand whose orders fall inside the requested window
Recommended fix
Add a covering index (created_date, order_name, total_price) — turns the scan into a range seek + covered read; tied to this exact query, not a blanket "add indexes" recommendation
Expected improvement
Order-of-magnitude — comparable small-brand queries hitting an equivalent covering index (idx_so_created_date_totalprice on other query shapes) run in the hundreds-of-ms range even on TMC's dataset
P0

Product Conversion Table scans the full catalog twice per page load, unpaginated

Endpoints
Product Conversion Table (initial load, every sort/filter change, CSV export) — productConversionService.js:241-348, 970-1082
Evidence
Code-audited: buildBaseCte's orders_60d CTE scans all of shopify_orders for the date range across every product with no per-product narrowing pushed in; doubles when a compare range is requested (separate previous_orders CTE)
Root cause
getProductConversion runs a COUNT query and a SELECT query independently, each re-materializing the same expensive CTEs from scratch — full scan runs twice (or 3-4× with a compare range) per page view; CSV export always runs unpaginated
Worse for large brands
Scales with total order/line-item rows in range × number of distinct products — the two dimensions that grow fastest for a large, established brand
Recommended fix
Compute the CTE result set once and reuse it for both the count and the page slice (e.g. a single query with a window function, or cache the materialized CTE result across the two calls within one request)
Expected improvement
~50% reduction in this endpoint's DB time from removing the duplicate scan alone, before any indexing work
P1

getDashboardSummary serializes 5-8 independent query branches

Endpoints
Main dashboard KPI row — every load (getDashboardSummary, metricsSnapshotService.js:2296-2424)
Evidence
Code-audited: totalPair, deltaPair, sales-channel pair, rowTwoComparison, its delta variant, intentPair, and two checkoutInitiatedPair calls are each independently awaited with no data dependency between them, instead of Promise.all'd
Root cause
Sequential coding style, not a data dependency — none of these branches' results feed into another's query
Worse for large brands
Each branch queries a large table (shopify_orders, hourly_sessions_summary_shopify, daily_user_intent_summary); serial execution multiplies per-branch latency by the number of branches taken instead of being bounded by the single slowest one
Recommended fix
Wrap the independent branches in Promise.all — no query rewrite needed, purely a control-flow change
Expected improvement
Wall-clock time drops from "sum of all branch latencies" to "slowest single branch latency" — for a dashboard load hitting 5+ branches, potentially 3-5×
P1

Payment Split Trend generates up to ~360 backend requests for one chart

Endpoints
Payment Split Trend chart, hourly and daily views (widgetDataHooks.js:1308-1552); the same pattern is duplicated for the Payment Composite metric in HourlySalesCompare.jsx:974-1033
Evidence
Code-audited: hourly view loops 24 hours × 2 endpoints × (1 or 2 for compare) = up to ~97 requests; daily view loops once per calendar day in the selected range × 2 endpoints × (1 or 2 for compare) — a 90-day range produces ~360 requests
Root cause
Client-side loop issuing one HTTP call per hour/day instead of one ranged call — the backend's getOrderSplit/getPaymentSalesSplit already accept start/end ranges elsewhere (useDashboardModeOfPaymentData uses this correctly)
Worse for large brands
Not brand-size dependent — this is a fixed multiplier (24 or N-days) regardless of data volume, but each of those N requests still pays the full per-request cost against a large brand's tables, so the two problems compound multiplicatively
Recommended fix
Replace the per-hour/per-day loop with a single ranged request per series (current, comparison), matching the pattern already used by useDashboardModeOfPaymentData
Expected improvement
Request count drops from ~97-360 to 2-4 for the same chart — the single largest reduction in raw request volume found in this audit
P2

alerts-service re-fetches the entire fcm_tokens collection on every notification

Endpoints
sendToAll (alerts-service/utils/fcm.js:45-145), called from every inventory alert, item-qty alert, and generic push event
Evidence
Code-audited: fcmTokensCollection.find({}).toArray() — no filter, no .limit(), no caching between calls; a single webhook payload with N breached thresholds triggers N full re-fetches (app.js:511-548)
Root cause
No token-list caching, and no TTL/last-seen cleanup for stale tokens — cleanup only happens reactively when FCM rejects a token as invalid
Worse for large brands
Not per-brand — scales with total registered devices org-wide, and with notification frequency (multiplied again by the N-alerts-per-webhook pattern)
Recommended fix
Cache the token list in-process with a short TTL, or push a `last_used`/TTL-based cleanup so the collection doesn't grow unbounded
Expected improvement
Not measurable without the collection's current size — flagged as a scaling risk more than a proven current bottleneck (see Section 9)

05 N+1 & Sequential-Operation Findings

Confirmed N+1 / per-item patterns

  • Multi-brand overview (overallSnapshotService.js:164-166) — one full getDashboardSummary() per accessible brand, parallelized across brands but ~8-10 serial round trips within each brand's call.
  • Inventory alert fan-out (alerts-service/app.js:511-548) — N breached thresholds in one webhook payload trigger N separate insertOne + N full fcm_tokens re-fetches + N FCM broadcasts.
  • Redis inventory cache refresh (alerts-service/app.js:175-207) — sequential for loop, one Redis SET per row, and sequential (not parallel) per-brand SQL queries in the all-brands refresh job. Background job, not request-path, but scales O(brands × rows/brand).

Sequential awaits with no data dependency (should be Promise.all)

  • getDashboardSummary — up to 8 independent branches, detailed in Section 3.
  • queryProductKpiTotals (metricsAggregateService.js:349-394) — orders, sessions, RTO queries awaited one at a time, no dependency between them.
  • getProductConversion's count vs. select queries (productConversionService.js:970-989) — independent, awaited sequentially, and each separately re-materializes the same CTEs (double cost, not just sequential cost).
  • Payment Split Trend's current-vs-comparison series (widgetDataHooks.js:1535-1552, HourlySalesCompare.jsx:997-1033) — frontend-side waterfall, comparison series only starts after current series fully resolves.

Current/previous period pairs done as two full executions instead of one conditional-SUM query

Most pair functions already use the efficient single-query pattern (WHERE (range1) OR (range2) + CASE/conditional SUM) — confirmed for queryOverallSummaryPair, queryUtmAggregatePair, queryDiscountAggregatePair, queryProductTypeAggregatePair, queryIntentSummaryPair. Three do not:

  • getReturnsSnapshotPair's UTM-filtered branch (metricsSnapshotService.js:877-898) calls computeReturnCounts twice — the non-UTM branch just below it (line 921) does it correctly in one query. An inconsistency between two paths for the same metric.
  • getSnapshotPair's generic fallback (product/device/snapshot filters active, metricsSnapshotService.js:2276-2291) calls getSnapshot() twice, each re-triggering its own full internal sub-query fan-out — the least efficient current/previous path in the codebase.
  • getDashboardSummary's cutoff-hour deltaPair and sales-channel pair (lines 2330-2367) re-run the entire pair machinery a second/third time instead of folding the extra condition into the already-computed totalPair.

06 Backend Processing Issues

  • Result-merging via in-memory Map instead of SQL JOIN — fetchDailyRows (3-4 queries merged via a byDate Map), fetchHourlyRows (3 queries via byKey), getDailyFunnel (up to 8-9 queries across 3 more Maps). None of the underlying tables are joined in SQL even though they share date/utm_source keys.
  • Over-fetch-then-filter-in-JS — Product Conversion's inventory-post-processing path (productConversionService.js:1005-1024) pulls every matching row with no LIMIT, then sorts/filters/paginates in Node; CSV export does the same unconditionally. getInventoryOnlyRowsFromRedis pulls the entire Redis inventory + sales cache into memory before filtering.
  • Scalar subquery per outer row — queryOverallSummaryTotals/Pair embeds a correlated subquery against hourly_sessions_summary_shopify inside the main query rather than a join; not unbounded, but a repeated-scan risk on wide date ranges.

07 Frontend Request Issues

Structural context worth stating plainly: App.jsx renders exactly one route/tab at a time via a single switch, and DashboardDataProvider already dedupes identical in-flight requests across sibling widgets on the Dashboard tab — both are good existing patterns, not findings.

  • Unthrottled global polling — NotificationsMenu.jsx polls /push/notifications every 15s for the entire session on every tab, with no document.visibilityState guard (unlike MerchantRequestsPanel, which does gate on visibility).
  • N+1 chart loops — Payment Split Trend, detailed in Section 3 (~97 requests hourly, ~360 requests for a 90-day daily range).
  • Duplicate pagespeed fetch path — DashboardRouteContainer.jsx's CSV snapshot download and widgetDataHooks.js's Web Performance widget independently call the same pagespeed endpoint outside DashboardDataProvider's cache, so clicking "Download Snapshot" while the panel is already showing refetches the same data.
  • Fetched-but-discarded rows — useDashboardWebVitalsData fetches full page-level pagespeed rows for the whole date range, then only uses the top 5 (and only when a single date is selected — otherwise the page-level fetch is thrown away entirely).

08 Database & Infrastructure Observations

  • Gateway auth is not a bottleneck. auth.authenticate() in the Lua layer does local JWT verification against a two-tier in-memory cache (verified-claims cache, ~300s TTL; JWKS/public-key cache, ~3600s TTL) — O(1) per request, no database or tenant-router call in the common case. The one exception is the /analytics/metrics/top-pdps "speed key" path, which always calls tenant-router.
  • tenant-router caches brand→DB-host resolution for 10 minutes per brand, LRU-capped at 500 distinct brands. Cost is amortized per brand, not per request — but if the org exceeds 500 concurrently-active brands, cache thrashing would reintroduce a resolution round-trip more often.
  • MySQL topology: tenant DBs are separate schemas on a shared RDS host/read-replica (read-replica-5...rds.amazonaws.com), one schema per brand, confirmed via live resolveTenantRoute calls — a single noisy/large brand's query load shares the same instance's CPU/IO with every other brand.
  • Not measurable in this environment: real production concurrent-request volume, database server CPU/memory/disk-IO graphs, network latency from EC2 to RDS under load, and event-loop-blocking behavior under concurrent traffic. This pass measured single-request, low-concurrency timings only.

09 Scaling Risks

Observed, not projected: the daily-funnel query's cost tracks shopify_orders row count closely enough that the 8-brand sample already shows the shape — smallest two brands (194-200ms COUNT(*), ~600ms funnel query) vs. largest (2.7s COUNT(*), 109.6s funnel query) is roughly a 14× row-count-proxy difference producing a ~170× query-time difference, consistent with a full index scan (cost grows with total table size, not with the 30-day window requested) rather than a range seek (cost would grow with window size only, roughly flat across brands for the same 30-day request).

This means the funnel/trend query's cost will keep climbing for TMC/PTS specifically as more orders accumulate, independent of anything the user does with date-range selection — a brand that's already large today is on the steep part of this curve, and the gap between it and small brands widens with every additional order, not just every additional feature.

Not independently measurable: Product Conversion Table's CTE cost at scale (flagged by code shape, not timed), fcm_tokens collection's actual current size, and whether the multi-brand overview endpoint's ~8-10-query-per-brand fan-out becomes the dominant cost once an org has many brands rather than one large one.

11 Optimization Roadmap

Sequenced by evidence strength and blast radius — nothing in this section has been implemented.

Phase A — Quick Wins

  • Add a covering index (created_date, order_name, total_price) on shopify_orders for the daily-funnel/trend query shape — directly tied to the measured 654ms→109.6s finding.
  • Wrap getDashboardSummary's independent branches (totalPair, deltaPair, sales-channel pair, row-two comparisons, intentPair, checkoutInitiatedPair ×2) in Promise.all — pure control-flow, no query changes.
  • Parallelize Payment Split Trend's current vs. comparison series with Promise.all (mechanical, halves wall-clock even before the loop itself is fixed).
  • Add a document.visibilityState guard to NotificationsMenu's 15s poll, matching the existing MerchantRequestsPanel pattern.

Phase B — Query & API Optimization

  • Replace Payment Split Trend's per-hour/per-day client loop with a single ranged or hourly-bucketed backend endpoint (the backend already supports ranged calls elsewhere — this is a frontend call-site change, not a new backend capability).
  • Restructure getProductConversion to materialize its CTEs once and reuse the result for both the count and the page slice, instead of two independent executions.
  • Fix the three current/previous "two full executions" cases (getReturnsSnapshotPair's UTM branch, getSnapshotPair's generic fallback, getDashboardSummary's cutoff/channel re-runs) to use the single conditional-SUM pattern already proven elsewhere in the same file.
  • Route the CSV snapshot's pagespeed fetch through the same DashboardDataProvider cache the on-screen widget uses.

Phase C — Architectural Optimization

  • Cache fcm_tokens in-process with a short TTL (or a Mongo change-stream–backed cache) instead of re-fetching the full collection per notification; add TTL/last-seen-based cleanup.
  • Evaluate replacing the fetchDailyRows/fetchHourlyRows multi-query-then-JS-Map-merge pattern with pre-aggregated tables or SQL-side joins where the same date/UTM key is already shared across the merged sources.
  • If the multi-brand overview endpoint becomes a bottleneck as brand count grows (not yet proven — see Section 9), consider a pre-aggregated per-brand summary refreshed on a schedule rather than computing all ~8-10 sub-queries live per brand per request.
Measured via direct MySQL connections from inside the running analytics-service container against 8 live tenant databases, plus static code audit across analytics, alerts-service, api-gateway, tenant-router, and client/dashboard. No indexes, caches, or code changes were applied during this audit.
